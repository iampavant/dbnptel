1. Database Basics

What is a Database?

A database is an organized collection of data that can be accessed, modified, and stored efficiently.

Real-World Analogy

Without Database: Papers scattered everywhere, hard to find anything

With Database: Organized filing system, find anything in seconds

Why Do We Need Databases?

  • Organization: Keep data in structured format
  • Speed: Find data instantly (not search through everything)
  • Consistency: Ensure data stays valid and correct
  • Multiple Users: Allow many people to access data simultaneously
  • Protection: Backup and recover from failures

Three-Level Architecture

Databases work in three levels:

VIEW LEVEL
What users see (custom views)
↕
LOGICAL LEVEL
What data exists (tables, columns)
↕
PHYSICAL LEVEL
Where data is stored (hard disk)

Example: Student Database

View Level: Student sees their own grades only

Logical Level: Tables: Student(ID, Name, GPA), Course(ID, Name), Grade(StudentID, CourseID, Mark)

Physical Level: Data stored in blocks on hard disk at specific locations

💡 Remember: View level hides complexity from users, logical level shows structure, physical level handles storage details.

ACID Properties

These 4 properties ensure database reliability:

Property Meaning Example
Atomicity All or Nothing Bank transfer: Both debit & credit happen, or neither
Consistency Valid state to valid state Total money in bank never changes (only moves)
Isolation No interference Two users can withdraw simultaneously without conflict
Durability Permanent after commit Power failure won't lose saved data

2. Understanding Tables (Relations)

What is a Relation?

A relation is just a table with rows and columns.

Terminology

Term Also Called Meaning Example
Table Relation Organized data structure Student
Column Attribute A characteristic or property Name, Email, GPA
Row Tuple / Record One complete record Alice, alice@x.com, 3.8
Cardinality - Number of rows 5 (if 5 students)
Degree Arity Number of columns 4 (StudentID, Name, Email, GPA)

Example: Student Table

StudentID Name Email GPA
S001 Alice alice@x.com 3.8
S002 Bob bob@y.com 3.5
S003 Carol carol@z.com 3.9

Breaking Down the Table:

Name: Student (the relation name)

Attributes: StudentID, Name, Email, GPA (4 columns)

Degree: 4

Cardinality: 3 (three rows/students)

A Tuple: (S001, Alice, alice@x.com, 3.8)

Properties of Relations

1. All values are atomic (no multiple values in one cell)

❌ Wrong: Courses = "Math, Physics, CS" (multiple values)

✅ Right: Each course in separate row

2. All rows are unique (no duplicates)

3. Row order doesn't matter

4. Column order doesn't matter

3. Keys in Databases

What is a Key?

A key is a unique identifier for a row. It helps us find and distinguish records.

Types of Keys

1️⃣ Primary Key (PK)

Definition: The main identifier chosen to uniquely identify each row.

Rules:

  • Must be UNIQUE (no duplicates)
  • Cannot be NULL (empty)
  • Should not change over time

Example: StudentID in Student table

2️⃣ Candidate Key

Definition: Any attribute or set of attributes that COULD be a primary key.

Example: In Student table, both StudentID and Email could be candidate keys (both unique)

But we choose only ONE as primary key

3️⃣ Foreign Key (FK)

Definition: A column that references a primary key in another table.

Purpose: Create relationships between tables

Example:

  • Department table: DeptID (PK)
  • Employee table: DeptID (FK) → references Department.DeptID

4️⃣ Super Key

Definition: Any set of attributes that contains a candidate key.

Key Rule: Super Key ⊇ Candidate Key (super keys are larger or equal)

Examples:

  • If StudentID is candidate key, then {StudentID} is super key
  • {StudentID, Name} is also super key (contains StudentID)
  • {StudentID, Name, Email} is also super key

Composite Key

Definition: A primary key made of multiple columns.

When Used: When no single column uniquely identifies a record

Example: Enrollment table

StudentID CourseID Grade
S001 C101 A
S001 C102 B
S002 C101 A

PK: (StudentID, CourseID)

Why? Because S001 can enroll in multiple courses, and C101 can have multiple students.

4. Relational Algebra

What is Relational Algebra?

Relational Algebra is a set of operations you can perform on tables to get new tables.

Analogy: Like arithmetic operations (+, -, ×, ÷) work on numbers, relational algebra operations work on tables.

Operation 1: Selection (σ)

Filters rows based on a condition (like WHERE in SQL)

Example:

Find students with GPA > 3.5

Notation: σ(GPA > 3.5)(Student)

Meaning: From Student table, keep rows where GPA > 3.5

Operation 2: Projection (π)

Selects specific columns (like SELECT in SQL)

Example:

Get only Name and Email from Student table

Notation: π(Name, Email)(Student)

Meaning: From Student, keep only Name and Email columns

Operation 3: Join (✶)

Combines two tables based on common columns

Example:

Combine Student and Enrollment on StudentID

Notation: Student ✶ Enrollment

Meaning: Match students with their enrollments

Operation 4: Cartesian Product (×)

Creates all possible combinations of rows from two tables

Example:

If Student has 3 rows and Course has 2 rows

Student × Course = 3 × 2 = 6 combinations

Note: Most combinations are not valid! This is why JOIN is better.

Important Concept: Join vs Cartesian

Key Rule:

Natural Join ⊆ Cartesian Product

This means: Join result is ALWAYS smaller or equal to Cartesian product

  • Join: Only matching rows
  • Cartesian: ALL combinations

5. SQL: Structured Query Language

What is SQL?

SQL is the language used to talk to databases. It translates relational algebra operations into human-readable commands.

Basic SQL Commands

1. SELECT (Projection)

Purpose: Choose which columns to display

SELECT Name, Email FROM Student;

Relational Algebra: π(Name, Email)(Student)

2. WHERE (Selection)

Purpose: Filter rows based on condition

SELECT * FROM Student WHERE GPA > 3.5;

Relational Algebra: σ(GPA > 3.5)(Student)

3. JOIN (Combine Tables)

Purpose: Connect rows from two tables

SELECT Student.Name, Course.CourseName FROM Student JOIN Enrollment ON Student.StudentID = Enrollment.StudentID JOIN Course ON Enrollment.CourseID = Course.CourseID;

Meaning: Get student names and their courses

4. GROUP BY (Aggregation)

Purpose: Group rows and calculate statistics

SELECT Department, COUNT(*) as EmployeeCount FROM Employee GROUP BY Department;

Meaning: Count employees in each department

Aggregate Functions

Function Purpose Example
COUNT(*) Count rows SELECT COUNT(*) FROM Student;
SUM(column) Add up values SELECT SUM(Salary) FROM Employee;
AVG(column) Average value SELECT AVG(GPA) FROM Student;
MAX(column) Largest value SELECT MAX(GPA) FROM Student;
MIN(column) Smallest value SELECT MIN(GPA) FROM Student;

6. Normalization

What is Normalization?

Normalization is the process of organizing data to eliminate redundancy and prevent data anomalies.

Analogy: Like organizing a messy closet - putting shoes together, clothes organized by season, etc.

Why Normalize?

Problem 1: Data Redundancy

StudentID Name CourseID CourseName
S001 Alice C101 Math
S002 Bob C101 Math

Problem: "Math" stored twice (redundancy)

Impact: Wasted space, inconsistency if "Math" changes

Problem 2: Update Anomaly

If "Math" changes to "Mathematics", must update in multiple places or data becomes inconsistent

Problem 3: Insertion Anomaly

Can't add a new course without a student

Problem 4: Deletion Anomaly

Deleting last student in a course loses the course information

Normal Forms (1NF → 2NF → 3NF → BCNF)

1NF - First Normal Form

Rule: All values must be atomic (single value per cell)

Problem Example:

StudentID Courses
S001 Math, Physics, CS

❌ Not 1NF: Multiple courses in one cell

✅ 1NF Solution:

StudentID Course
S001 Math
S001 Physics
S001 CS

2NF - Second Normal Form

Rule: 1NF + No partial dependencies

Partial Dependency: Non-key attribute depends on PART of composite key

❌ Not 2NF Example:

StudentID CourseID CourseName
S001 C101 Math

PK: (StudentID, CourseID)

Problem: CourseName depends only on CourseID (not full key)

✅ 2NF Solution: Decompose

Table 1: Enrollment

StudentID CourseID

Table 2: Course

CourseID CourseName

3NF - Third Normal Form

Rule: 2NF + No transitive dependencies

Transitive Dependency: Non-key depends on another non-key

❌ Not 3NF Example:

StudentID Name MajorID MajorName

Problem: MajorName depends on MajorID (non-key), not on StudentID

✅ 3NF Solution: Decompose

Table 1: Student

StudentID Name MajorID

Table 2: Major

MajorID MajorName

7. B+ Trees for Indexing

What is an Index?

An index is a data structure that speeds up data retrieval.

Analogy: Like a book's table of contents - instead of reading all 500 pages, you look up the page number and jump there directly.

Why Indexes Matter

Without Index (Linear Search)

  • Check first record: Not a match
  • Check second record: Not a match
  • ...continue for all records...
  • Time: O(n) - proportional to number of records

With B+ Tree Index

  • Start at root of tree
  • Go left or right based on comparison
  • Reach leaf in few steps
  • Time: O(log n) - logarithmic (much faster!)

What is a B+ Tree?

A balanced tree structure where:

  • All leaves are at same level
  • Each node can have multiple keys and children
  • All searches start at root and end at leaf
  • Provides very fast search - O(log n)

B+ Tree Structure Example

[50] / \ [20] [70] / | \ / | \ [10][20][30][70][75][90]

8. Transactions & ACID

What is a Transaction?

A transaction is a sequence of operations that must complete together (all or nothing).

Real-World Example: Bank Transfer

Transfer $100 from Account A to Account B

✅ WITH Transaction:

  • Debit A by $100
  • Credit B by $100
  • COMMIT (both complete)

If power fails before COMMIT: Both operations undo automatically

❌ WITHOUT Transaction:

  • Debit A by $100 ✓
  • CRASH! Power failure
  • Credit B by $100 ✗ (never happens)

Result: $100 lost! 😱

ACID Properties

A = Atomicity (All or Nothing)

Transaction either completes fully or not at all.

✓ Both operations complete

✗ Both operations undo

Never: One completes, other fails

C = Consistency (Valid State to Valid State)

Database moves from one valid state to another.

Example: Total money in bank never changes (only moves)

Before: A=500, B=300, Total=800

After: A=400, B=400, Total=800 ✓

I = Isolation (No Interference)

Concurrent transactions don't interfere with each other.

Example: While T1 transfers $100, T2 checking balance sees either before or after state, never intermediate.

D = Durability (Permanent)

Once committed, data survives failures.

After COMMIT, even power failure won't lose the saved data.

Transaction States

Active
↓
Partially Committed
↙ ↘
Committed ✓
Aborted ✗

Transaction Serialization

When multiple transactions run simultaneously, the result should be the same as if they ran one after another.

Example: T1 and T2 transferring money

Sequential (safe) Concurrent (might conflict)
T1 completes → T2 starts T1 and T2 run together
Results consistent Must ensure same result as sequential

9. Recovery Systems

What is Recovery?

Recovery is the process of restoring database to a consistent state after a failure.

Logging

A log records every change made to the database.

Log Entry Format:

<TransactionID, DataItem, OldValue, NewValue>

<T1, A, 100, 200> // T1 changed A from 100 to 200 <T1, B, 50, 75> // T1 changed B from 50 to 75 <T1, COMMIT> // T1 committed

Undo and Redo Operations

UNDO: Revert Change

Use OLD value to reverse a change.

Log: <T1, A, 100, 200>

UNDO: Set A back to 100

When: Transaction failed and needs rollback

REDO: Reapply Change

Use NEW value to reapply a change.

Log: <T1, A, 100, 200>

REDO: Set A to 200 again

When: Transaction committed but data not written to disk

Checkpoints

A checkpoint is a snapshot that marks a "known good" point in database.

Timeline:

T1: Write(A) T2: Write(B) --- CHECKPOINT {T1, T2} --- T3: Write(C) T3: COMMIT --- CRASH ---

At checkpoint:

  • T1, T2 updates are on disk
  • This is our "known good" state
  • We can start recovery from here

Recovery Process

Step 1: Identify What to Do

Transaction Status Action Why
Committed BEFORE checkpoint NO ACTION Already on disk from checkpoint
Committed AFTER checkpoint REDO Apply their changes again
No commit (any time) UNDO Reverse their changes
